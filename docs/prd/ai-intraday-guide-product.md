# PRD — AI 단타 가이드 상품화

## 1. 배경·문제

현재 `/intraday`는 운영자용 모의투자 표와 자동 포트폴리오 상태가 중심이다. AI가 어떤 종목을 얼마에 몇 주 사고팔았는지는 기록되지만, 일반 사용자가 지금 해야 할 행동을 즉시 파악하기 어렵다. 또한 AI의 가상 체결과 사용자가 실제로 가이드를 따라 했다는 사실을 구분하는 원장이 없어, “매수를 따라 한 사용자에게만 이후 매도 가이드를 준다”는 상품 경험을 만들 수 없다.

## 2. 목표

- 첫 진입에서 `오늘 이용권 → 가이드 시작`의 상품 구조를 이해시킨다.
- 시작 후 가장 최근의 미응답 매수·매도 가이드를 알림 카드로 최상단에 보여준다.
- 사용자는 `수행했어요` 또는 `이번엔 넘길게요`로 응답한다.
- AI의 가상 체결 원본과 사용자 응답 원장을 분리한다.
- 사용자가 수행한 매수를 기준으로 가이드 보유 수량을 계산하고, 보유한 종목의 매도 가이드만 노출한다.
- 기존 종목 검색·추천 후보·상세 모의투자 표는 `직접 분석 도구` 아래의 보조 흐름으로 유지한다.

## 3. 범위와 사용자 흐름

### 3.1 시작 전

1. 사용자는 `오늘의 AI 단타 가이드` 상품 카드에서 이용 시간, 분석 주기, 기준 금액, 가격을 확인한다.
2. 기준 금액만 수정할 수 있다. 종목 수·위험 모드·판단 주기는 기본 정책으로 숨긴다.
3. `오늘 가이드 시작하기`를 누르면 기존 오토파일럿 런을 시작한다.
4. 실제 PG가 연결되지 않은 환경에서는 `결제 연동 전 체험 화면`임을 명시한다. 결제 완료를 가장하거나 실제 과금을 암시하지 않는다.

### 3.2 진행 중

1. 상단에는 `진행 중`, 다음 분석 예정, 분석 종목 수, 수행 중 보유 종목 수를 한 줄로 표시한다.
2. 미응답 가이드가 있으면 가장 최근 1건을 큰 알림으로 표시한다. 나머지는 `대기 N건`으로 축약한다.
3. 매수 가이드는 종목명, 기준가, 수량, 예상 금액, 손절 기준, 짧은 근거를 표시한다.
4. `수행했어요`를 누르면 종목·수량·가격을 다시 보여주는 인라인 확인 단계를 거친 후 저장한다.
5. `이번엔 넘길게요`는 즉시 패스 처리한다. 패스한 매수는 가이드 보유에 포함하지 않는다.
6. 매도 가이드는 사용자가 수행한 매수로 계산된 가이드 보유 수량이 1주 이상일 때만 표시하며, 수량은 해당 보유 수량을 상한으로 한다.
7. 응답한 가이드는 최신순 활동 내역에 남는다.

### 3.3 종료

- 사용자가 `오늘 가이드 종료`를 누르거나 장 마감 정책이 실행되면 신규 가이드 생성을 멈춘다.
- 수행 이력과 가이드 보유 요약은 당일 기록으로 남긴다.
- 본 변경은 실제 증권사 주문을 실행하지 않는다.

## 4. 데이터·상태 모델

### 4.1 원본과 응답의 분리

- **추천 원본**: 기존 `PaperTradingTick.orders[]`. AI 가상 체결의 불변 원본이다.
- **사용자 응답**: `AutopilotRun.guideResponses[guideId]`. 수행/패스 사실만 기록한다.
- **guideId**: `${sessionId}:${tickId}:${orderIndex}`. 같은 추천은 재시도해도 같은 ID를 갖는다.
- 응답은 서버가 원본 세션·틱·주문을 다시 조회해 ticker, side, 가격, 수량을 확정한다. 클라이언트가 보낸 가격·수량은 신뢰하지 않는다.

### 4.2 상태 전이

```text
추천 원본 생성 → pending
pending → performed | passed
performed/passed → 변경 불가
```

- 동일 `guideId`에 같은 응답을 재전송하면 기존 결과를 반환하는 멱등 처리다.
- 서로 다른 응답으로 재전송하면 `409`로 거절한다.
- `performed SELL`은 그 시점까지의 수행 원장상 보유 수량이 1주 이상일 때만 허용한다.
- 화면의 보유 수량은 수행 BUY 합계 − 수행 SELL 합계로 계산하며 0 미만이 될 수 없다.

### 4.3 레거시 호환

- 과거 런에는 `guideResponses`가 없을 수 있으므로 빈 객체로 취급한다.
- 런 payload JSON 확장으로 저장하며 새 DB 컬럼이나 마이그레이션을 요구하지 않는다.

## 5. 기능 요구사항·수용 기준

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| AC-1 | 상품 진입 | 시작 전 카드에서 오늘 이용권·운영 시간·분석 방식·가격·체험 상태를 한 화면에 이해할 수 있다. |
| AC-2 | 단일 CTA | 시작 전 필수 입력은 기준 금액 하나이고 핵심 CTA는 한 개다. |
| AC-3 | 알림 우선 | 진행 중 미응답 최신 가이드 1건이 첫 화면에서 가장 높은 시각 위계를 갖는다. |
| AC-4 | 명확한 행동 | 가이드 카드에 종목·매수/매도·가격·수량·예상금액·근거·시각이 표시된다. |
| AC-5 | 수행 확인 | `수행했어요`는 인라인 재확인 후 서버 원장에 저장된다. |
| AC-6 | 패스 | `이번엔 넘길게요`는 해당 추천만 패스하고 이후 다른 추천을 막지 않는다. |
| AC-7 | 매도 연계 | 수행한 매수가 없는 ticker의 매도 가이드는 행동 카드에 나타나지 않고 서버도 수행 저장을 거절한다. |
| AC-8 | 멱등 | 동일 guideId·동일 응답 재시도는 중복 기록을 만들지 않는다. 상충 응답은 409다. |
| AC-9 | 원장 분리 | AI 가상 주문과 사용자 수행 기록은 서로 다른 필드에 저장되며 기존 가상 수익률 계산을 변경하지 않는다. |
| AC-10 | 활동 내역 | 대기/수행/패스를 구분해 최신순으로 표시하고, 대기는 상단 행동 카드와 중복 강조하지 않는다. |
| AC-11 | 기존 도구 | 검색·후보·표·관리자 캘리브레이션은 제거하지 않고 `직접 분석 도구` 보조 영역에 유지한다. |
| AC-12 | 반응형·접근성 | 390px와 1280px에서 CTA·가격·상태가 잘리지 않고, 버튼·라이브 상태·확인 영역에 접근 가능한 이름이 있다. |
| AC-13 | 한글·면책 | ticker 외 사용자 문구는 한글이며 실제 주문 아님·수익 비보장·PG 미연동을 명시한다. |
| AC-14 | 연구용 모의투자 분리 | 상품 시작과 별도로 `모의투자 시작` 진입점을 유지하고, research 런은 수행/패스 없이 장중 가상 체결 원장을 계속 쌓는다. |

## 6. 비목표

- 실제 결제/환불/영수증/구독 관리.
- 증권사 주문 API 연동 또는 사용자의 실제 체결 여부 자동 검증.
- 기존 AI 판단·스크리너·가상체결 알고리즘 변경.
- 여러 기기·사용자 계정 단위의 가이드 원장 분리. 현재 오토파일럿의 운영자 owner 경계를 그대로 사용한다.

## 7. 측정·운영

- 시작 전 → 가이드 시작 전환율.
- 추천별 응답률, 수행률, 패스율, 평균 응답 시간.
- 수행 BUY 이후 SELL 가이드 도달률과 왕복 완료율.
- 미응답 가이드 최대 적체 수와 오래된 미응답 비율.
- 결제 도입 전에는 가격을 실험용 표시값으로만 취급하고 매출 지표로 사용하지 않는다.

## 8. 영향 분석

- UI: `IntradayAutopilotCard`를 상품 진입·가이드 피드 중심 경험으로 교체하고 기존 워크스페이스를 보조 영역으로 낮춘다.
- API/BFF: 기존 `/api/paper-trading/autopilot/[runId]` PATCH에 guide response 명령을 추가한다.
- 타입: `AutopilotRun`에 optional `guideResponses`를 추가한다.
- 서버: 런 owner, 자식 세션, tick/order 원본, 매도 가능 수량을 검증한 뒤 write-through 한다.
- 데이터: 기존 `paper_trading_autopilot_runs.payload` JSON에만 추가되어 SQL 변경이 없다.
- 실행 목적: 런 payload의 optional `purpose`로 `guide`와 `research`를 구분하며, 레거시 런은 `research`로 해석한다.
- 보안: 브라우저는 same-origin axios만 사용하고 서버가 수량·가격을 원본에서 재구성한다.

## 9. OPEN QUESTION

1. 오늘 이용권 가격은 얼마인가? **PM 권고: UI 실험값 9,900원으로 시작하되 PG 연결 전에는 체험임을 병기한다.** 실제 가격 확정 시 카피 상수 한 곳만 변경한다.
2. 사용자가 실제로 다른 가격·수량에 체결했다면 수정 입력을 받을 것인가? **PM 권고: MVP는 추천 수량·가격 수행 여부만 받는다.** 임의 입력은 원장 오류와 조작 비용을 키운다.
3. 패스를 되돌릴 수 있게 할 것인가? **PM 권고: MVP는 불가.** 수행은 재확인으로 오클릭을 막고, 응답 원장을 단방향으로 유지한다.
4. 미응답 추천을 언제 만료할 것인가? **PM 권고: 같은 ticker의 다음 반대 방향 주문 또는 당일 종료 시 UI에서 과거로 낮춘다.** 서버 응답 상태 자체는 불변으로 남긴다.

## 10. 5회 기획 리뷰와 반영

### 리뷰 1 — AI 체결과 사용자 수행이 섞이는 문제

- 발견: 기존 order에 `performed`를 덧붙이면 가상 포트폴리오가 사용자 실제 보유처럼 해석될 수 있다.
- 수정: 기존 tick/order는 불변 원본으로 두고 `guideResponses`를 별도 원장으로 분리했다.

### 리뷰 2 — 매수를 안 따라 한 사용자에게 매도하라는 문제

- 발견: 기존 엔진은 가상 포지션 기준으로 매도하므로 사용자의 실제 행동과 불일치한다.
- 수정: 수행 BUY − 수행 SELL로 가이드 보유를 계산하고, 보유가 없는 ticker의 SELL은 UI에서 숨기며 서버에서도 거절한다.

### 리뷰 3 — 네트워크 재시도와 더블클릭으로 기록이 중복되는 문제

- 발견: 클릭마다 새 응답 ID를 만들면 같은 추천이 여러 번 수행될 수 있다.
- 수정: session/tick/order index 기반 결정적 guideId, 동일 명령 멱등, 상충 명령 409 규칙을 추가했다.

### 리뷰 4 — 알림이 누적되어 지금 할 일이 묻히는 문제

- 발견: 모든 추천을 같은 카드 크기로 나열하면 장중에 판단이 느려진다.
- 수정: 최신 미응답 1건만 큰 행동 카드로 올리고 나머지는 대기 수·컴팩트 활동 내역으로 낮췄다.

### 리뷰 5 — 결제되지 않았는데 유료 이용권처럼 보이는 문제

- 발견: 가격과 `결제 후 시작` 문구만 넣으면 실제 과금·환불이 있는 것으로 오해할 수 있다.
- 수정: CTA는 `오늘 가이드 시작하기`, 가격 옆에는 `결제 연동 전 체험`을 명시하고 실제 PG는 비목표로 고정했다.
